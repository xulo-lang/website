## Overview

Tests live in the same source files as the code they check. The language contributes exactly two things to testing — the `#Test` form and the `assert` intrinsic — so that a test is checked with the rest of the program and discoverable from the source itself. Everything else — which tests a tool discovers, the order it runs them, what each run is isolated from, and how a failure is reported — belongs to the tool, not to the language. There is no test framework to learn and no assertion library to install.

## Test functions

A test is a function marked with `#Test`. It appears at file scope, among a module's top-level declarations — it is not a statement and appears nowhere else:

```js
#Test
fn mapGetAnswersNull() {
  let m = { a: 1 }
  assert(map_get(m, "z") == null, "absent key is null")
}
```

The head token is exactly `#Test`, and the optional `async` marker follows it (`#Test async fn`, never `async #Test fn`). The examples write `#Test` on its own line directly above `fn`, and that placement is **RECOMMENDED** — the attribute marks the whole declaration and reads better apart from the signature; `#Test fn name() { … }` on one line is equally well-formed.

A test function has a fixed shape — nothing is optional beyond `async`:

| Slot | Rule |
|------|------|
| parameters | none: the list is empty |
| return type | none: the body is an implicit `fn(): Unit` |
| `pub` | none: a test is never part of an interface |
| generics / `where` | none |

The form carries no other attributes — `#Derive #Test fn` is not a test. A `#Test` before an `fn` with parameters, a return type, generics, a `where` clause, or `pub` parses as an ordinary `fn` carrying the attribute and is diagnosed `E0110` (`` attribute `Test` takes the form `#Test [async] fn name() { … }` ``); written on a `struct`, `enum`, `trait`, or `impl` it is `E0109`.

- **Always checked.** The body is checked exactly as a `fn(): Unit` body is checked — types, exhaustiveness, mutability, the statement-value rule — whether or not any tool ever runs it. A file whose tests do not check is rejected like any other file. The body is the body of an implicit nullary function returning `Unit`: `return` alone is accepted, and `return e` checks `e` against `Unit`.
- **The name binds no value.** The identifier is the test's identity as a tool reports it, not a callable name: any reference to it — a call, a value use, a path — is a compile-time error (`E0107`). A check that would recurse is written as an ordinary helper function that the test calls. Two tests in a module MAY share a name; a tool tells them apart by their positions.
- **Inert.** No execution of the program evaluates a test body — not the module's initializers, not `main`, not any call: the name binds no value, so nothing can reach it. Statements in a test body run only under a tool.
- **Same view of the module.** The body sees the file's `use` bindings and its module-level declarations under the same scope and forward-reference rules as any function body.

```js
#Test
fn referenceIsForbidden() {
  assert(true, "runs only under a tool")
}

fn main() {
  referenceIsForbidden() // error: `referenceIsForbidden` is a test function and cannot be referenced (E0107)
}
```

## Async tests

A test whose body suspends is marked `async`; the marker follows `#Test` (`#Test async fn`, never `async #Test fn`) and is spelled exactly as `async` is spelled on a function:

```js
#Test
async fn delayedTaskFinishes() {
  await Time::sleep(1) // ok: an async test body is an async context
}

#Test
fn awaitNeedsTheAsyncMarker() {
  await Time::sleep(1) // error: `await` outside of an `async` context (E0501)
}
```

With the marker the body is an `async` context exactly as an `async fn(): Unit` body is; without it, `await` is `E0501`. When a tool runs the test, the body starts as its own task.

## `assert`

| Signature | Result |
|-----------|--------|
| `assert(condition: Boolean, message: String): Unit` | `Unit` |

- Arguments are checked and evaluated left to right like any other call: `message` is evaluated whether or not `condition` holds.
- When `condition` is `false`, the call stops the program with `panic(message)` — the same effect as writing that `panic` directly ([Error Handling](/en/docs/reference/stdlib/error-handling/)).
- When `condition` is `true`, the call has no effect beyond producing `Unit`.

```js
let xs = [2, 4, 6]
assert(list_size(xs) == 3, "three items") // ok: no effect
assert(list_size(xs) == 4, "not four")    // false: stops with panic("not four")
```

`assert` is how a `#Test` body states a requirement. It is an intrinsic, like `print`, `println`, and `str`: available without `use`, exactly one signature, and the name is reserved — a module-scope declaration MUST NOT bear it (`E0106`).

## What Counts as Failure

A test passes or fails by one criterion, fixed by the language:

| Outcome | Condition |
|---------|-----------|
| **pass** | the body runs to completion — for an `async` test, when the task its body started settles as completed |
| **fail** | a `panic` or a runtime failure stops the body, or — for an `async` test — that task settles as cancelled |

`panic` and runtime failures behave inside a test body as they do anywhere else: they stop the execution that reached them — here, the running of that test. A false `assert` is such a panic, so it fails the test with its message. Cancellation carries no error at all; an `async` test whose task is cancelled simply fails.

## What Stays in the Tool

The specification fixes only the declaration, the checking, and the pass/fail criterion. Everything around a run is the tool's, and outside the specification:

- which tests a tool discovers, and from which files
- the order they execute in
- what each run is isolated from (state, environment, other tests)
- what a tool reports, and how it renders a failure
- whether a run continues after a failure

The language guarantees only that a test body is inert until a tool runs it and that it is always checked — no tool can suppress a test that does not compile.

## Examples

```js
// The pair differs only in the marker: rejected at check time vs. accepted
#Test
fn awaitNeedsTheAsyncMarker() {
  await Time::sleep(1) // error: `await` outside of an `async` context (E0501)
}

#Test
async fn awaitWithTheAsyncMarker() {
  await Time::sleep(1) // ok: the test passes when its task completes
}

#Test
fn referenceIsForbidden() {
  assert(true, "runs only under a tool")
}

fn main() {
  referenceIsForbidden() // error: `referenceIsForbidden` is a test function and cannot be referenced (E0107)
}
```

The last test is well-formed on its own; the call in `main` is rejected (`E0107`), and the test body is still checked and still runs only under a tool.

```js
#Test
fn listOpsRoundTrip() {
  let mut xs = ["a", "b"]
  list_push(xs, "c")
  assert(list_size(xs) == 3, "three items")
  assert(list_remove(xs, 0) == "a", "removed head")
  assert(list_size(xs) == 2, "two remain")
}

#Test
async fn deadlineReportsTimeout() {
  let outcome = await Task::timeout(Time::sleep(5000), 50)
  match outcome {
    Result::Err(e) => assert(e.message == "timed out", "Err carries the timeout message")
    Result::Ok(_) => panic("deadline did not expire")
  }
}
```
