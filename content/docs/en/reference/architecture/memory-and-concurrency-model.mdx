## Overview

Xulo's runtime model answers two questions: what a binding denotes, and how tasks share storage.

- **Storage is managed automatically.** A value lives while it is reachable and is reclaimed when nothing can reach it. There is no manual free, no destructor, and no observable reclamation.
- **Ownership is explicit where it matters.** `move` severs a binding from its value, `copy` produces a deep copy, and every parameter borrows its argument for the duration of the call.
- **Concurrency is structured.** `async` calls and `spawn` produce `Task<T>` values, every block settles the tasks started inside it before it finishes, and the only storage two tasks can both reach is a `shared` region guarded by `lock`.

This page is a practical summary; the normative text is [Memory and Runtime](/en/docs/spec/memory-and-runtime/), [Concurrency](/en/docs/spec/concurrency/), and [Error Handling](/en/docs/spec/error-handling/). Async syntax and `Task` utilities are covered in [Async & Tasks](/en/docs/reference/architecture/async-and-tasks/).

## Value semantics and reference semantics

Every type has one of two categories, and the category decides what a binding denotes.

| Category | Types | `let x = e` and assignment |
|----------|-------|----------------------------|
| **Value** | `bool`, `string`, `int`, `float`, `number`, fixed-bit numerics, `null`, `unit`, `struct`, `enum`, `Array<T, N>`, `Range<T>`, tuples | a fresh, independent copy of `e`'s value; a `struct`, `enum`, `Array`, or tuple copy is shallow — each field or element is copied by its own category |
| **Reference** | `List<T>`, `Map<K, V>`, `Set<T>` | the same value, shared: `x` and `e` then denote the one underlying value |

Four further values carry **identity** rather than content — function values (closures), `Task<T>`, `View`, and `Error` — and behave as references to a single, distinct thing: two such values are equal only when they are the same value. `copy` of an identity-carrying value is the same value, so there is no way to clone a task in flight or to split a closure's captured storage by copying it.

```js
struct Point { x: int, y: int }

let a = Point(x: 1, y: 2)
let mut b = a        // b holds an independent copy of a's value
b.x = 9
print(a.x)           // 1: the write through b never reaches a

let xs = [1, 2, 3]
let ys = xs          // ys and xs denote the same list
let mut zs = ys
zs[0] = 9
print(xs[0])         // 9: the write through zs is visible through xs
```

Consequences:

- Value-semantic values cannot be aliased: a write through one binding is never observable through another.
- Reference values are shared: a write through any mutable place naming the value is visible through every other binding naming it. Independence is obtained explicitly with `copy`.
- Arguments are independent of this table: a parameter *borrows* its argument and never copies it, whatever the category.

`==` compares by content for every value-carrying type — element-wise for tuples and `Array`, following references for collections, terminating on cyclic values — and by identity for the four identity-carrying values. Arrays of different lengths are different types, so comparing them is `E0211`. A comparison of unrelated types is a compile-time error (`E0211`).

## Ownership with `move`

`move` transfers ownership: it produces the value of its operand and invalidates the binding it came from. From then on the binding has been **moved out**, and any use of it is a compile-time error (`E0403`).

- The operand MUST be a path naming a binding. `move p.x`, `move xs[0]`, and `move compute()` are errors: a transfer moves a whole binding, never a part of one.
- The binding MUST be one the current frame owns: a `let`, `let mut`, `const`, loop, or pattern binding. A parameter borrows its argument and owns no storage to transfer, so `move p` where `p` is a parameter is an error (`E0403`).
- `move` is accepted in exactly three positions: the initializer of a `let`, an argument of a call, and the operand of `return`. In any other position — a condition, a binary operand, a field initializer, a literal element — it is `E0403`.
- `move` and `copy` are prefix operators at the `unary` precedence level, so `move a + b` groups as `(move a) + b` and the position rule then rejects it.
- `move` applies to every category. For a value-semantic value the transfer is not observable through other bindings (there are none); for a reference value it is: after the move, no binding of the moving scope denotes that value.

```js
fn consume(data: List<int>): int {
  data[0] * 2
}

fn main() {
  let items = [1, 2, 3]
  let n = consume(move items)   // ownership transfers to the call
  print(n)                      // 2
  // print(items)               // error: `items` has been moved (E0403)
}
```

The one place where `move` is *required* is capture into a `spawn` block (see [Capture](#capture-into-a-spawn-block)).

## Ownership with `copy`

`copy` produces an independent deep copy of its operand's value: a fresh value in which every reachable content-bearing part has been duplicated, so later writes through either copy are invisible to the other.

- Deep copying follows references through `List`, `Map`, and `Set` values, through `struct` and `enum` fields, through tuple elements, and through `Array` elements. Copying a cyclic structure terminates: the copy graph mirrors the original.
- Identity-carrying values — function values, `Task<T>`, `View`, `Error` — are not duplicated: the copy is the same value.
- `copy` accepts any expression as its operand and, like `move`, appears only as a `let` initializer, a call argument, or a `return` operand. `copy` of an already value-semantic value is redundant but legal.

```js
let alice = { name: "Alice", age: 30 }
let bob = copy alice      // an independent deep copy
```

## Borrowing

A parameter never receives its argument's storage; it *borrows* it for the duration of the call — extended past the call's return when the call returns a `Task`, as [Span end](#span-end) defines.

| Form | Meaning |
|------|---------|
| `p: T` | **immutable borrow** — the default: the callee may read, not write |
| `p: mut T` | **mutable borrow** — exclusive write access for the duration of the call |
| `self` / `mut self` | method receiver, written the same way: `self` borrows immutably, `mut self` mutably |

A parameter is an ordinary binding for every purpose but ownership: it MAY be passed on, where it lends its borrow to the inner call for that call's duration — an immutable parameter lends an immutable borrow, a `mut` parameter a mutable one. Onward lending obeys the same rules as the original call.

Borrowing obeys **aliasing XOR mutability**: at any moment a value is either shared by any number of immutable borrows or held by at most one mutable borrow, never both. Three rules make that checkable; in them, a place is **used** when it is read, written, moved, or passed as an argument.

1. **A mutable borrow needs a mutable place.** An argument passed to a `mut` parameter — or supplied as a `mut self` receiver — MUST be a place backed by a `mut` binding. Passing a literal, a computed value, or an immutable binding is a compile-time error (`E0404`).
2. **One call borrows without overlap.** Two arguments of one call MUST NOT denote overlapping places when either of the two parameters is `mut`; using a place this way is a compile-time error (`E0404`). When two places overlap is defined under [Overlap](#overlap).
3. **Borrows span suspension.** A borrow begins when the call starts and ends when the callee returns — or, when the call returns a `Task`, when that task settles ([Span end](#span-end)). While a **mutable** borrow of a place is outstanding, code outside the callee MUST NOT use the place at all (`E0405`). While an **immutable** borrow is outstanding, code outside the callee MUST NOT write the place (`E0411`) and MUST NOT start a mutable borrow of it (`E0404`); reads remain unrestricted. The same spans apply to a `let mut` binding written by an `async` closure that has suspended: the binding is borrowed by the running body until the closure's task settles.

```js
struct Counter { value: int }

fn bump(p: mut Counter) {
  p.value = p.value + 1
}

fn main() {
  let mut c = Counter(value: 0)
  bump(c)                    // mutable borrow of c for the call
  print(c.value)             // 1: the borrow ended with the call
}
```

Many immutable borrows may be outstanding at once — reads through them are unrestricted. Ordinary reference sharing between bindings is not a borrow and is always allowed:

```js
async fn peek(xs: List<int>) {
  print(xs[0])
}

async fn watch(mut xs: List<int>) {
  let t = peek(xs)           // immutable borrow of xs, until t settles
  // xs[0] = 9               // error: written during an immutable borrow (E0411)
  print(xs[0])               // ok: reads remain unrestricted
  await t                    // the borrow ends here
  xs[0] = 9                  // ok
}
```

### Overlap

Two places overlap unless, walking their paths from the base, the first position where they differ proves them disjoint:

- different field names — `a.x` and `a.y` — or, in tuples, different positions — `p.0` and `p.1`;
- the same list subscripted by two distinct integer literals — `xs[0]` and `xs[1]`.

Any pair whose paths do not diverge this way overlaps: the same binding; one path a prefix of the other (`a` and `a.x`); the same field (`a.x` and `a.x.y`); subscripts that are not two distinct literals (`xs[i]` and `xs[j]`, or `xs[i]` and `xs[0]`). Overlap is a static judgment: two non-literal indices are never assumed distinct.

```js
fn pair(a: mut int, b: int): int { a + b }

fn overlap(mut xs: List<int>, i: int) {
  pair(xs[0], xs[1])         // ok: distinct literal subscripts are disjoint
  pair(xs[0], xs[0])         // error: the same place, mutably borrowed twice (E0404)
  pair(xs[0], xs[i])         // error: a non-literal index is never assumed distinct (E0404)
}
```

### Span end

A borrow from a call that returns a `Task<U>` — an `async` call, an `async` closure call, or a synchronous call whose result type is `Task<U>` — lasts until the checker can see that task settle. It can see it where control flow reaches a point after an `await` whose operand contains the task's binding: `await t`, `await Task::all([t, u])`, and `await Task::timeout(t, ms)` each wait for `t`. When the scope contains no such `await`, the borrow lasts until the scope ends, by which time the scope's exit has settled the task.

- The synchronous case is conservative: the callee MAY have stored a borrowed place inside the task it returned, so the checker cannot end the borrow at the call even though the callee has returned; with no `await` of the task, the borrow lasts to the scope end.
- Flow decides: on a path that has not reached such an `await` — the other branch of an `if`, an earlier loop iteration — the borrow is still outstanding.

```js
async fn fill(p: mut List<int>) {
  p[0] = 7
}

async fn main() {
  let mut xs = [0]
  let t = fill(xs)                    // mutable borrow of xs
  // xs[0] = 1                        // error: the borrow is outstanding (E0405)
  await t                             //   until this await is reached
  xs[0] = 1                           // ok: the borrow has ended
}
```

## Mutability rules

`mut` belongs to a binding or a parameter, never to a type — and never appears at a call site: `bump(c)`, not `bump(mut c)`.

- A place is **mutable** when the binding at the base of the path is a `let mut`, a `mut` parameter, or the `mut self` receiver of the running call; a field or subscript inherits the mutability of its base. Everything else is immutable, and assigning to it is a compile-time error (`E0401`).
- A closure may assign through a captured binding only when that binding was declared `let mut`. A `mut` parameter or `mut self` is a mutable place for direct assignment but is not declared `let mut`: assigning to it through a closure capture is a compile-time error (`E0401`), which admits read capture only.
- Value-semantic storage belongs to one binding, so mutation through a `mut` place changes only that binding's copy. Reference-semantic storage is shared, so a mutation through any mutable place naming it is visible through every binding naming that value.
- A `const` is immutable and has no mutable form; a shadowing `let mut` of the same name is an ordinary new binding.
- Across tasks, mutation of one value is permitted only through the shared-state discipline — `shared` bindings and `lock` — below. The borrow rules govern a single running task.

## Lifetimes (informal)

Xulo has no lifetime annotation; storage outlives every use that can be written. *Lifetime* is used only to say when something is usable:

- A binding's usable life runs from its declaration to the end of its block; using it earlier or after a `move` is a compile-time error (`E0403`).
- A borrow lives exactly as long as its call — or, when the call returns a `Task`, until that task settles, as [Span end](#span-end) defines — and no use outside the callee can name it, because borrows are parameters, not values that can be stored.
- A closure captures by reference: captured bindings become part of the closure's value and their storage remains valid for as long as the closure is reachable, even beyond the frame that created them.
- Because storage is reclaimed only when it is unreachable, no program can hold a reference to freed memory: dangling references do not exist, and neither use-after-free nor double-free is a possible failure.

## Garbage collection

Storage is managed automatically. Memory becomes eligible for reclamation when it is unreachable from any root — a live binding, a running or suspended call frame, a closure, a task, or a shared region — and is reclaimed at an unspecified time thereafter.

- A value reachable from anywhere is kept: a returned closure keeps its captures alive, a suspended task keeps its frame alive, and a shared region lives while any binding or task names it.
- There is no explicit deallocation, no destructor, and no operation that frees memory early; a program cannot observe reclamation, and no program behavior depends on when it happens.
- How an implementation reclaims — tracing, reference counting with cycle collection, region-based bulk reclamation, or any combination — is not fixed; only the guarantee above is. A mechanism that never reclaims a value unreachable from every root does not conform.
- Allocation strategy is likewise free: values no later pass of the program can reach — a replaced computation's tree, the frame of a settled task — MAY be allocated in a region reclaimed in bulk when that boundary is crossed, and an implementation SHOULD keep any single reclamation pause within limits it documents. Neither the strategy nor the pause is observable.
- Deterministic *release of a resource* — a file, a connection — is a library concern expressed with ordinary control flow: cleanup is written on each path that needs it or registered once with `defer`, because the language provides no destructor. The language itself manages only storage.

## Runtime failures

A runtime failure stops the program where it occurs: it is a `panic` raised by the implementation, and — like the program's own `panic(...)` — it has no handler.

| Condition | When it occurs |
|-----------|----------------|
| List index or length out of range | a subscript `xs[i]` with `i` negative or at or past the list's length; a `splice` or `slice` index/count outside its stated bounds; or a negative `resize`/`truncate` length |
| Array index out of bounds | reading or writing `a[i]` where `i` is negative or at or past `N` |
| String index out of range | `s.codeAt(i)` with an index outside `0 … s.len − 1`, or `s.slice(start, end)` with bounds outside `0 … s.len` or with `start > end` |
| Division or remainder by zero | `/` or `%` on non-constant operands whose value is zero |
| Shift amount out of range | `<<` or `>>` whose amount is negative or at or past the operands' bit width, on non-constant operands |
| Arithmetic overflow | an `int` or fixed-bit operation whose result exceeds its type, on non-constant operands |
| `std::math::toFixed` digits out of range | `std::math::toFixed` is called with `digits` outside `0...=15` |
| Unprovided environment key | reading an `@Environment` key no provision supplies |
| Stack or task exhaustion | recursion depth or the runtime's task limit is exceeded |
| Lock misuse | a task acquires a `lock` it already holds (locks are not reentrant) |
| Task exhaustion | the runtime's limit on live tasks is exceeded while spawning |

The recursion and live-task limits behind the exhaustion rows are implementation-defined, as is how a failure is presented (message text, stream, and the exact nonzero exit status). Expected failures are not runtime failures: they travel as `Result` values and are handled with `match` or `?`.

## Exit status

The language has no I/O and no `exit` function; how a program ends is nevertheless pinned:

- A program that terminates normally — `main` returns `unit`, the task returned by an `async` `main` settles, or the presentation target of a `View` program closes — exits with status **0**.
- A runtime failure that ends the program — a panic, and with it any condition of the table above — exits with a **nonzero** status. The exact nonzero values, and how the failure is presented to the environment, are implementation-defined.

## Tasks

A **task** is a unit of asynchronous computation with type `Task<T>`.

- Calling an `async` function or closure starts its body in the current task's context; `await` is the only suspension point the language exposes.
- `spawn` starts work whose body is not part of any call: the spawning expression yields a `Task` immediately, the body runs as its own task, and the task settles when the body completes or is cancelled.
- Tasks are values: a `Task<T>` may be stored, passed, returned, and awaited later. A task that is never awaited leaves its result unused and is not thereby cancelled.

## The `spawn` expression

`spawn` has five forms — four that run a block, and one that starts a service:

```js
spawn async { Block }
spawn.thread async { Block }
spawn.process async { Block }
spawn.on(Pool) async { Block }
spawn.process Type { FieldInit , … }
```

| Form | Runs the block |
|------|----------------|
| `spawn async { … }` | on the default task scheduler |
| `spawn.thread async { … }` | on an operating-system thread |
| `spawn.process async { … }` | in a separate process |
| `spawn.on(pool) async { … }` where `pool` has type `fn(fn(): unit): unit` | where `pool` decides |
| `spawn.process Type { … }` | as a service of type `Type` (see [Services](#services)) |

- The `async` keyword is required in the block forms, and the block is an `async` context: `await` is legal inside it wherever it is legal inside an `async` function body.
- The first four forms are expressions of type `Task<T>`, where `T` is the type of the block. The service form evaluates to a service handle.
- The dispatch mode selects the **executor** that runs the block's segments (see [Executors](#executors)). Capture, scope, and cancellation rules are identical in every mode.
- `spawn` is an ordinary expression: it may appear in a synchronous or an `async` body, in any expression position its type permits.
- A `spawn` expression is not `unit`, so — like every non-`unit` expression — it may not stand alone as an expression statement. Bind it, `await` it, or pass it on.

```js
async fn main() {
  let first = spawn async { weight(3) }
  let second = spawn.thread async { weight(4) }
  print(await first + await second)   // 7
}
```

### Executors

The dispatch mode selects the executor that runs the block: the default task scheduler, an operating-system thread, a separate process, or a caller-supplied pool. The service form produces no task; its process is governed by [Services](#services). A task's execution is a sequence of **segments**: the body runs until it completes or suspends at an `await`, and each segment is handed to the task's executor when the task becomes ready — once when the `spawn` expression is evaluated, and once more after each `await` in the block completes.

- A segment runs from the task's current position to its next suspension or to settlement. The executor MAY begin the segment before the call that hands it over returns; `spawn` itself yields the `Task` without waiting for any segment to finish.
- The block's result is carried by the `Task`, never by the executor: the `fn(): unit` a pool receives runs one segment and returns `unit`, and the value the block produces is stored in the task when it settles.
- `spawn.thread` runs each segment on an operating-system thread, which MAY be released when the segment ends and MAY differ from segment to segment. No language rule depends on which thread a segment runs on.
- `spawn.process async { … }` runs segments on the new process's own scheduler, and the block's result is carried back to the `Task` in the spawning process when the block settles.
- A task cancelled while its next segment waits in an executor settles as cancelled when that segment runs; the body does not resume.

## Capture into a `spawn` block

A `spawn` block is not a closure. It does not see the bindings of the scope that surrounds it; it must be given what it uses.

- Always visible inside a block, without capture: declarations (`fn`, `struct`, `enum`, `trait`, `impl`, `type`), `const` bindings, and the prelude's intrinsics and names.
- Every other enclosing binding — a parameter, a local `let` or `let mut`, a module-level `let` or `let mut` — MUST be captured before the block's body may use it. A capture is written as a `let` initializer in the block: `let local = move config` or `let local = copy config`. Mentioning an uncaptured enclosing binding anywhere else in the block is a compile-time error (`E0408`).
- `move` transfers ownership: the capture is evaluated when the `spawn` expression is evaluated, and the enclosing binding is moved out; using it after the `spawn` is an error (`E0403`).
- `copy` takes a snapshot at the same moment and leaves the enclosing binding usable.
- A `shared` binding needs no capture form: the block captures the shared region itself, and its contents are reachable only under `lock`.

Capture is decided when the `spawn` expression is evaluated, before the body runs, so what a block receives never changes while it executes:

```js
fn upload_files(): Task<unit> {
  let config = load_config()
  let data = gather()
  let job = spawn.thread async {
    let local_config = move config   // captured when the spawn runs
    let local_data = copy data       // a snapshot; `data` stays usable
    transmit(local_data, local_config)
  }
  print(data)                        // legal: `data` was copied, not moved
  // print(config)                   // error: `config` has been moved (E0403)
  job                                // returned: this task outlives the scope
}
```

## Scopes and structured concurrency

Every block is a **scope** for the tasks started inside it — by `spawn` or by an `async` call — including a function or closure body and the body of `main`. When a block finishes, it does not simply stop: it settles its tasks first, then runs its `defer`s.

1. The block's value, if any, is determined.
2. Each task started in the block that has not settled is cancelled.
3. The block waits until every one of those tasks has settled.
4. Each settled child contributes nothing further: a child that settled as cancelled is absorbed, and a result no longer reachable from the block's value is discarded.
5. Each `defer` registered in the block runs, in reverse order of registration (LIFO): the last one written runs first.
6. The block's value is produced.

A `defer` registers cleanup (`defer close(f)`) that runs when control leaves its block — the block's end, a `return`, a `break` or `continue`, a `?` early return, or a cancellation stop at an `await` — innermost block first, each block's defers in reverse order of registration. A block's defers run after its value has been determined and after its tasks have settled, so cleanup observes a finished block. **A `panic` runs no defers:** the program stops where the `panic` is written, and every defer whose operand has not begun is abandoned.

A task **reachable from the block's value** is exempt from step 2: it is not cancelled, and its ownership passes to the enclosing scope together with the value, where the same rules apply. This is how a function returns a task it started — whether by `spawn` or by an `async` call.

Three consequences:

- **Parent cancellation propagates downward.** Cancelling a task cancels the scope inside its body, which cancels that scope's tasks in turn.
- **The program ends when `main` returns.** `main` may be declared `async`; when it is, the program ends when its task settles — completed or cancelled — by which time its body's scope has already drained. Work that must finish before exit is awaited inside the scope that owns it.
- **Services outlive the block that started them.** A service is not a task: a block's completion neither cancels nor stops it, and its lifetime is governed by its handle ([Service lifetime and `stop`](#service-lifetime-and-stop)).

## Cancellation

Cancellation is cooperative and requested only by the language — when a scope exits — and propagates to a cancelled task's own scope.

- A cancelled task stops at its next `await`: the pending `await` produces no value and the task settles as cancelled. A task that is running continues until it suspends.
- Before it settles, a cancelled task runs the defers registered in its live blocks — innermost block first, each in reverse order of registration. An `await` inside such a defer ends that run where it stands: the remainder of that defer and every defer still waiting are abandoned, and the task settles.
- Cancellation carries no error value: no expression observes it, nothing raises it, and there is nothing to catch. The body runs as written between the cancellation request and its next `await`.
- Cancellation is final: a cancelled task settles as cancelled whatever its body does afterwards, and a value the body produces after settling is discarded.
- `await` of a cancelled task stops the awaiting body at that `await`, which produces no value, and the awaiting task settles as cancelled in turn — the propagation continues outward through every `await` until a scope absorbs it or a cancelled `main` ends the program.
- A scope that cancels its own children absorbs their cancellation: they settle as cancelled and the scope continues normally.
- Cancellation cannot interrupt code between suspension points: a body that never awaits again runs to completion even though it has been cancelled.

## Shared state and `lock`

Concurrent tasks mutate one value only through a **shared region** guarded by a lock. `shared` is part of a binding form, exactly as `mut` is: it appears in a `let` and in a parameter declaration, and it adds no type — a shared binding of `AppState` has type `AppState`.

```js
let state = shared Expr          // a shared binding
fn f(state: shared T, …)         // a shared parameter
lock state { Block }             // a critical section
```

- The contents of a shared binding — every field and subscript reached through it — MAY be read or written only while the current task holds the lock on that binding: lexically inside `lock state { … }` on that very binding, or inside a function called from such a section that receives the region as a `shared` parameter. Any other access is a compile-time error (`E0406`).
- Inside `lock state { … }` the contents reached through `state` are mutable places, whether or not the binding is `let mut`; assignment through them follows the ordinary place rules.
- The operand of `lock` MUST be a shared binding (`E0407`), as must an argument passed to a `shared` parameter.
- `lock` is an expression: its value is the value of the block, so a section both mutates and produces. The lock is released when the block finishes — normally, or by `return`.
- A `lock` body contains no suspension point: `await` inside `lock` is a compile-time error (`E0410`). A critical section therefore runs from entry to exit without yielding, and cancellation — which takes effect at a task's next `await` — cannot interrupt one.
- Acquiring a lock never suspends the acquiring task. On a runtime that runs several tasks on one thread, two tasks on that thread can never contend for one binding's lock; on a runtime that runs tasks in parallel, the executing thread waits — blocked or spinning — until the section in progress finishes. Because that section contains no `await`, the wait is bounded by its duration. Waiting this way is not a suspension point, so `await` remains the only one.
- Locks are not reentrant: acquiring a lock the current task already holds is a runtime failure (lock misuse, above).

```js
struct AppState { total_online: int, names: List<string> }

fn join(state: shared AppState, name: string) {
  lock state {
    state.total_online = state.total_online + 1
    state.names = state.names + [name]
  }
}

fn report(state: shared AppState): int {
  lock state { state.total_online }
}

async fn main() {
  let state = shared AppState(total_online: 0, names: [])
  let one = spawn async { join(state, "Ada") }
  let two = spawn async { join(state, "Lin") }
  await one
  await two
  print(report(state))      // 2
}
```

Sections should be short, and a task that needs several locks SHOULD acquire them in a consistent order; tasks that wait on one another's locks make no further progress.

## Memory visibility and atomics

Xulo exposes no atomic types, no fences, and no memory-order parameters. Nothing of the kind is needed: the checker confines every access to shared storage inside a `lock` on that binding (`E0406`, `E0407`), spawn blocks capture by `move` or `copy` rather than by reference, and service messages are deep-copied in transit — so a shared region guarded by its lock is the only storage two tasks can both reach, and every access to it is already ordered by construction.

An implementation MAY use atomics, fences, operating-system locks, or a single thread internally; none of that is observable. What it MUST preserve is the ordering the language does state:

- **Within a task**, operations are sequenced: operands, arguments, and literal elements evaluate left-to-right, statements run in source order, and module-level initializers run in declaration order before `main`.
- **Across a lock**, critical sections on one shared binding are ordered: the writes performed inside a `lock state { … }` are visible to every critical section on `state` that begins after it finishes, whichever task performs it.
- **By value**, everywhere else: the result of `await`, a settled task's result, and a message are values carried between tasks, not shared storage.

Data-race freedom is therefore a consequence of the static rules, not an obligation the programmer carries.

## Services

A **service** is an actor: a struct with an `on_message` method, running in its own process, reached only by sending messages.

```js
struct Tally { total: int }

impl Tally {
  fn on_message(mut self, cmd: int) {
    self.total = self.total + cmd
    reply(self.total)
  }
}

async fn main() {
  let worker = spawn.process Tally { total: 0 }
  let sum = await worker.send(41)
  print(sum)                        // 41
  worker.stop()
}
```

- `spawn.process Type { field: expr, … }` starts a service of the struct type `Type`. The field list initializes the service's state; it is evaluated left-to-right, and the constructed value is deep-copied into the new service, so the service never shares storage with its spawner.
- `Type` MUST declare `on_message` in an `impl` block; a service type without one is a compile-time error (`E0409`). The method takes a receiver (`self` or `mut self`) and exactly one message parameter; it MAY be declared `async`.
- The spawn evaluates to a **service handle**: a value of the structural type `{ send: fn(M): Task<R>, stop: fn(): unit }`, whose `stop` member ends the service ([Service lifetime and `stop`](#service-lifetime-and-stop)).
- `handle.send(m)` copies the message value into a message, queues it for the service, and returns a `Task<R>` immediately. The message is deep-copied in transit and the sender's value is unaffected; `send(move x)` transfers ownership instead — no copy is performed, and any later use of `x` is a compile-time error (`E0403`), exactly as after any other `move`. Because the copy completes before `send` returns, the argument's borrow ends with the call and does not span the returned task.
- The queue of messages waiting for a service is unbounded: `send` never waits for capacity and never fails because the queue is full. A client that needs backpressure limits how many sends it leaves unanswered.
- The returned `Task<R>` MAY stand alone as a statement: `handle.send(m)` in statement position is fire-and-forget — the message was queued when the call evaluated, so only the reply goes unread, and the block settles the task on exit.
- A `send` performed after the service has stopped is discarded immediately and its task settles as cancelled, exactly like a message still queued when the service stopped.
- A service handles one message at a time, in arrival order: `on_message` runs to completion — through every `await`, if it is `async` — before the next message begins.
- `reply(e)` may be called only inside `on_message`. The reply type `R` is the common type of the `reply` operands in the method, or `unit` when the method never calls `reply`. The send's task settles when `on_message` returns, carrying the reply value — or, when the executed path performed no `reply` although the method contains `reply` calls, settling as cancelled.
- Cancelling a send task does not withdraw a message already queued.

Messages are the only channel: there is no shared state between a service and its clients, so a service never needs `shared` or `lock`.

### Service lifetime and `stop`

A service is not bound to the block that started it. It runs until it is stopped through its handle or until the program ends:

- Completing the block that evaluated the `spawn.process` expression does not stop the service. The handle may be stored, passed, and used after that block has finished — including from a later iteration of a loop whose body started the service.
- `handle.stop()` requests that the service stop. Stopping is cooperative, following the same rule as a cancelled task: the service finishes its current synchronous run and stops at its next `await`. A body that never awaits again runs to completion, and the service has stopped when `on_message` returns.
- When a service stops, every message still queued is discarded, and each discarded message's send task settles as cancelled. A `reply` performed by the path that was executing is unaffected.
- `stop` is idempotent: calling it on a service that has already stopped — or from several holders of the handle — has no further effect.
- When the program ends, every service that has not stopped is stopped and its queued messages are discarded.

## Scheduling, determinism, and undefined behavior

Nothing about scheduling is language-visible. Programs MUST NOT depend on which ready task runs next, which of several racing tasks settles first, how many run concurrently, how long a suspension lasts, the iteration order of `Set<T>`, or when storage is reclaimed.

What this model does fix, for every conforming program:

- **Evaluation order** — left-to-right for operands, arguments, and literal elements; source order for statements; declaration order for module initializers.
- **Scope completion** — a block finishes only after the tasks started inside it have settled and its defers have run.
- **Collection order** — `Map` entries iterate in insertion order, and `Task::all` yields results in argument order.
- **Termination of the structural operations** — `==` and `copy` halt on cyclic values.

Programs are deterministic when they do not depend on the unspecified items — that is, when they do not race.

**This model defines no undefined behavior.** For every program that passes the static checks, evaluation order and results are the ones fixed above, and every condition that can stop a computation at run time is one of the runtime failures in the tables on this page — a specified failure with a specified cause, after which the computation has ended.

Exactly one boundary sits outside that promise: during an [extern call](/en/docs/reference/ecosystem/ffi-and-interop/), what the foreign code itself does — memory it touches, values it produces, effects it has on the host — is neither specified nor checked here. The Xulo side of that call stays inside the promise: every argument expression, every conversion to an ABI-safe type, and the result conversion are fully specified. Nothing else in the language crosses this boundary.

Four choices are implementation-defined and MUST be documented: the recursion and live-task limits, how exhaustion of resources the language does not model (available memory above all) is detected and reported, how a runtime failure is presented to its environment — message text, stream, and the exact nonzero exit status — since the language itself has no I/O, and which ABI document each registered tag (`"C"`, `"system"`) denotes on the target platform — and therefore the pointer width that `usize` and `isize` have.
