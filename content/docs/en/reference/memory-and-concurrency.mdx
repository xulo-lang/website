## Design Philosophy

**Normative Reference**: The keywords *SHALL*, *MUST*, *SHOULD*, and *MAY* used in this specification follow [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

XULO adopts a **No Garbage Collection (No GC)** and **strong Ownership & Borrowing** memory management model to achieve deterministic resource release and zero-cost abstractions.

### Why No GC?

While garbage collectors (GC) reduce the cognitive burden of memory management, they introduce unpredictable pauses (Stop-the-World), memory fragmentation, and additional runtime overhead. XULO takes a different approach:

- **Deterministic Release**: Resources are freed immediately when leaving scope, no waiting for GC cycles
- **Zero Runtime Overhead**: Ownership checks happen at compile time with zero runtime cost
- **Predictable Performance**: Suitable for real-time systems, game engines, high-frequency trading, and other latency-sensitive scenarios

### Smart Defaults Principle

To reduce developer cognitive load, the language follows the **"Smart Defaults"** principle:

1. **Explicit Semantics, Symbol-Free Syntax**: Rejects punctuation pollution like `&`, `&mut`, `*`, using clear English keywords uniformly
2. **Immutable Borrow by Default**: Without any modifier, value passing defaults to an **Immutable Borrow**, with no deep copy (Copy) or ownership transfer (Move)

This means most function calls are zero-cost — you don't need to remember whether each function produces a copy, because the default behavior is safe borrowing.

## Memory Access Modifiers

### Basic Ownership Semantics

In single-threaded and local scopes, variable and parameter passing follows these 4 basic forms:

| Form / Syntax | Standard Semantics | Access Rights | Low-level Mapping (Rust/C++) | Description |
| --- | --- | --- | --- | --- |
| **`u: T`** | Immutable Borrow *(Default)* | Shared Read-only (`Read`) | `&T` | **Default form**. Zero keywords, no ownership transfer, no memory copy. |
| **`u: mut T`** | Exclusive/Mutable Borrow | Exclusive Writable (`Read/Write`) | `&mut T` | Declares exclusive modification rights to the original memory object. |
| **`move expr`** | Ownership Transfer | Ownership Transfer (`Transfer`) | `move` / T | Completely transfers resource ownership; the original scope variable immediately becomes invalid (Compile Error). |
| **`copy expr`** | Explicit Deep Copy | Independent Copy (`Clone`) | `.clone()` | Clones a brand-new memory on heap/stack, completely severing ownership ties with the original variable. |

### Example: Comparing the Four Forms

```js
struct User {
    name: string
    age: number
}

// 1. Immutable borrow (default)
fn print_user(u: User) {
    print(u.name)  // Read-only access
}

// 2. Mutable borrow
fn birthday(u: mut User) {
    u.age += 1  // Exclusive modification
}

// 3. Ownership transfer
fn consume(u: User) {
    // u's ownership is transferred to this function
    // u is freed when function ends
}

// 4. Explicit deep copy
fn clone_user(u: User): User {
    copy u  // Create independent copy
}

fn main() {
    let mut alice = User { name: "Alice", age: 30 }
    
    print_user(alice)        // Immutable borrow, alice still valid
    birthday(mut alice)      // Mutable borrow, alice still valid
    let bob = copy alice     // Deep copy, alice and bob independent
    consume(move alice)      // Ownership transfer, alice invalid
    // print_user(alice)     // Compile error: alice has been moved
}
```

### Aliasing XOR Mutability Rule

The compiler enforces the following borrowing rules at compile time (violation triggers a compile error):

- **Rule 1**: At any given scope and point in time, an object may have **unlimited immutable borrows (`u: T`)**
- **Rule 2**: At any given scope and point in time, an object may have **at most one mutable borrow (`u: mut T`)**
- **Rule 3**: Mutable borrows and immutable borrows **cannot coexist**

### Example: Rule Verification

```js
struct Config {
    debug: boolean
    log_level: number
}

fn example() {
    let mut config = Config { debug: true, log_level: 3 }
    
    // ✅ Correct: Multiple immutable borrows can coexist
    let r1 = config
    let r2 = config
    let r3 = config
    print(r1.debug)
    print(r2.log_level)
    print(r3.debug)
    
    // ❌ Error: Immutable and mutable borrows cannot coexist
    let r = config
    let m = mut config  // Compile error: config is already borrowed as immutable
    m.debug = false
}

fn example2() {
    let mut config = Config { debug: true, log_level: 3 }
    
    // ✅ Correct: Mutable borrow takes effect after immutable borrow ends
    {
        let r = config
        print(r.debug)
    }  // r's borrow ends here
    let m = mut config  // Now we can get a mutable borrow
    m.debug = false
}

fn example3() {
    let mut config = Config { debug: true, log_level: 3 }
    
    // ❌ Error: Multiple mutable borrows in same scope
    let m1 = mut config
    let m2 = mut config  // Compile error: config is already borrowed mutably
    m1.debug = false
}
```

### Scopes and Lifetimes

The lifetime of a borrow is strictly limited by its scope. When a borrow leaves its scope, it is automatically released:

```js
fn process() {
    let mut data = list<number> { 1, 2, 3 }
    
    // Borrow scope is delimited by curly braces
    {
        let view = data  // Immutable borrow starts
        print(view.length)  // Use the borrow
    }  // Borrow ends, view invalid
    
    // Now we can modify directly
    mut data.push(4)  // Explicit mutable operation
}
```

## Multi-Threading Model

To prevent **data races** in multi-threaded scenarios, the compiler enforces strict safety boundaries on cross-thread dispatch (`spawn`) through type inference.

### Core Challenges of Thread Safety

Multi-threaded programming faces three core challenges:

1. **Data Races**: Multiple threads accessing the same memory, with at least one thread writing
2. **Dangling References**: Thread A holds a pointer that is freed by Thread B
3. **Memory Visibility**: Thread A's modifications are not visible to Thread B

XULO solves these problems at compile time through its ownership system, with no runtime detection needed.

### spawn Dispatch Modes

`spawn` is a built-in keyword supporting four dispatch modes, covering the full spectrum from lightweight coroutines to heavyweight processes:

```js
// 1. Default: Lightweight Async Task (90% of use cases)
spawn async {
    do_work()
}

// 2. Dispatch to OS Physical Thread
spawn.thread async {
    compute_heavy_matrix(move data)
}

// 3. Dispatch to Independent Child Process (Actor)
spawn.process async {
    run_sandboxed_plugin()
}

// 4. Dispatch to Custom Thread Pool / Scheduler
spawn.on(my_custom_pool) async {
    handle_request()
}
```

| Mode | Syntax | Underlying Implementation | Use Case |
| --- | --- | --- | --- |
| **Default** | `spawn async { ... }` | Lightweight Async Task | I/O-bound, high concurrency (90% of cases) |
| **Thread** | `spawn.thread async { ... }` | OS Physical Thread | CPU-intensive computation, blocking operations |
| **Process** | `spawn.process async { ... }` | Independent Child Process | Sandbox isolation, plugin system, crash isolation |
| **Custom** | `spawn.on(pool) async { ... }` | Custom Scheduler | Specific thread pools, priority queues |

### Ownership Transfer Mode

Ordinary variables (not wrapped in `shared`) must explicitly transfer ownership via the **`move`** keyword when dispatched across threads.

**Constraint**: Once a variable is `move`d into a `spawn` task block, the main thread and other threads immediately lose access to that variable.

```js
fn spawn_worker() {
    let config = load_config()
    let data = process_data(config)
    
    // ✅ Correct: Use move to transfer ownership
    spawn async {
        let local_config = move config  // config ownership transferred
        let local_data = move data      // data ownership transferred
        upload(local_data, local_config)
    }
    // config and data are invalid here
    
    // ❌ Error: Attempting to access moved ownership
    // print(config.debug)  // Compile error: config has been moved
}
```

### Thread-Safe Shared Containers

When multiple threads need to simultaneously access and modify the same memory object, it must be wrapped with the **`shared`** keyword, and a **`lock`** must declare a critical section.

- **`shared` Declaration**: Constructs a shared container with thread-safe atomic reference counting and mutual locking mechanisms (equivalent to `Arc<Mutex<T>>`)
- **`lock` Scope**: The `lock` keyword declares an exclusive critical section. Inside the `lock` scope, internal data is exposed as mutable (`mut`); when the scope ends, the mutex is implicitly released (RAII mechanism)

```js
struct AppState {
    total_online: number
    active_users: list<string>
}

// Example: Thread-safe shared state and modification
let global_state = shared AppState {
    total_online: 0,
    active_users: []
}

// Thread 1: Increment online user count
spawn async {
    lock global_state {
        global_state.total_online += 1
    }
}

// Thread 2: Add user
spawn async {
    lock global_state {
        global_state.active_users.push("Alice")
    }
}
```

### Internal Mechanism of shared

The `shared` keyword creates a thread-safe reference-counted container under the hood:

```js
// Conceptual implementation of shared (not real syntax)
struct Shared<T> {
    data: T,
    ref_count: AtomicUsize,  // Atomic reference count
    lock: Mutex<()>          // Exclusive lock
}

// Usage with automatic management
let state = shared AppState { total_online: 0 }
// ref_count = 1

spawn async {
    // Cross-thread capture implicitly increments shared container's ref_count (ref_count = 2)
    lock state {
        state.total_online += 1
    }
    // state leaves spawn scope, ref_count = 1
}
// state leaves main scope, ref_count = 0, memory freed
```

### Avoiding Deadlocks

The `lock` scope is designed to be as small as possible to minimize lock hold time:

```js
// ✅ Recommended: Minimize lock scope
fn update_state(state: shared AppState) {
    // Only hold the lock when necessary
    let new_value = {
        lock state {
            let current = state.value
            current + 1
        }  // Lock released here
    }
    
    // Other computation outside the lock
    let processed = heavy_computation(new_value)
    
    lock state {
        state.result = processed
    }
}

// ❌ Not recommended: Overly long lock scope
fn bad_example(state: shared AppState) {
    lock state {
        state.value += 1
        let result = heavy_computation()  // Expensive operation inside lock
        state.result = result  // Unnecessary lock hold
    }
}
```

## Multi-Processing & Sandbox Isolation Model

XULO's multi-process model follows a **Shared-Nothing** architecture, implementing physical-level memory isolation and crash isolation.

### Why Multi-Processes?

While multi-threading is efficient, it has critical drawbacks:

1. **Crash Contagion**: A segmentation fault in one thread crashes the entire process
2. **Shared Memory**: Threads share memory, so memory corruption in one thread can affect others
3. **Debugging Difficulty**: Multi-threaded bugs are hard to reproduce and debug

The multi-process model solves these problems through physical isolation.

### Channel Communication

Processes communicate with threads/child processes via channels (`channel`).

**Data Serialization**: All data sent through a `channel` is **implicitly copied and serialized** at send time. The receiver parses it as a completely new memory object, eliminating cross-process memory pointer dependencies entirely.

```js
// Main process: Create channel using channel.channel<T>() factory function
let ch = channel.channel<Command, Result>()

// Start child process (pass channel handle to WorkerService)
let worker = spawn.process WorkerService { id: 1, channel: ch }

// Send command (auto-serialized)
ch.send(Command.Analyze("hello"))

// Receive result
let result = ch.receive()
print(result)
```

The more common pattern is to directly use the handle returned by `spawn.process` with its built-in `.send()` method:

```js
// Main process: Communicate directly via handle, no explicit Channel creation needed
let worker = spawn.process WorkerService { id: 1 }

// Handle has built-in .send() method, cross-process auto-serialization
worker.send(Command::Analyze("important data"))

// Synchronously wait for response
let result = worker.send_sync(Command::Analyze("data"))
```

### Process Service Declaration

Developers can define independent process service entities (Actor model) using **`struct` + `impl`**. Child processes have their own event loops and memory spaces; their crash behavior does not cause the main process to die.

```js
// 1. Define standard message types and response structures
enum Command {
    Analyze(string),
    Shutdown,
    Crash
}

// 2. WorkerService is a regular struct with process logic
struct WorkerService {
    // Internal state isolated within the process
    metrics: Metrics
}

impl WorkerService {
    // Process message loop callback
    fn on_message(u: mut self, cmd: Command) {
        match cmd {
            Command::Analyze(data) => {
                let result = heavy_analysis(data)
                reply(result)
            }
            Command::Shutdown => {
                reply(Status::ShuttingDown)
            }
            Command::Crash => {
                panic("Simulated crash")
            }
        }
    }

    fn on_error(err: Error) {
        print("Worker error: " + err.message)
        reply(Status::Error)
    }
}

// 3. Main process usage
fn main() {
    // Use spawn.process primitive to launch Worker entity in isolated process sandbox
    let worker = spawn.process WorkerService { metrics: Metrics.new() }

    // Send message (cross-process auto-serialized and deep copied)
    worker.send(Command::Analyze("important data"))

    // Crash isolation: even if worker process crashes severely, main process remains safe
    try {
        let result = worker.send_sync(Command::Crash)
    } catch (e) {
        print("Worker crashed, but main process is safe")
    }
}
```

### Inter-Process Communication Patterns

XULO supports multiple IPC patterns:

```js
// 1. Request-Response pattern
struct Calculator {
    result: number
}

impl Calculator {
    fn on_message(u: mut self, msg: { op: string, a: number, b: number }) {
        let result = match msg.op {
            "add" => msg.a + msg.b,
            "mul" => msg.a * msg.b,
            _ => 0
        }
        reply(result)
    }
}

fn main() {
    let calc = spawn.process Calculator { result: 0 }
    let sum = calc.send_sync({ op: "add", a: 10, b: 20 })
    print(str(sum))  // 30
}

// 2. Publish-Subscribe pattern
struct EventBroker {
    subscribers: list<channel.Handler>
}

impl EventBroker {
    fn on_message(u: mut self, msg: Subscribe) {
        u.subscribers.push(msg.channel)
        reply(Status::Ok)
    }

    fn on_message(u: mut self, msg: Publish) {
        for sub in u.subscribers {
            sub.send(msg.data)
        }
        reply(Status::Ok)
    }
}
```

## Complete Code Example

The following code demonstrates how memory modifiers, multi-threading, and multi-process work together in XULO:

```js
// 1. Immutable borrow (zero keywords)
fn inspect(u: User) {
    print(u.name)  // Read-only access, zero cost
}

// 2. Mutable borrow (only mut)
fn update_profile(u: mut User, new_name: string) {
    u.name = new_name  // Exclusive modification
}

// 3. Ownership transfer function
fn transfer_ownership(u: User) {
    // u's ownership is within this function
    save_to_database(u)
    // u is freed when function ends
}

fn main() {
    // === Single-threaded Memory Management ===
    let mut local_user = User { name: "Alice", age: 20 }
    
    // Immutable borrow: zero cost, local_user still valid
    inspect(local_user)
    
    // Mutable borrow: exclusive modification
    update_profile(mut local_user, "Bob")
    
    // Explicit deep copy: create independent copy
    let user_backup = copy local_user
    
    // === Multi-threaded Concurrency ===
    
    // Scenario 1: Ownership transfer to async task
    spawn async {
        save_to_database(move local_user)
    }
    // local_user has been transferred, accessing again triggers compile error
    
    // Scenario 2: Thread-safe sharing
    let app_metrics = shared Metrics { requests: 0 }
    
    // Multiple threads safely concurrent modification
    spawn async {
        lock app_metrics {
            app_metrics.requests += 1
        }
    }
    
    spawn async {
        lock app_metrics {
            app_metrics.requests += 1
        }
    }
    
    // === Multi-process IPC ===
    
    // Start independent process service
    let worker = spawn.process WorkerService { id: 1 }
    
    // Send message via handle (auto-serialized)
    worker.send(Command::Analyze)
    
    // Crash isolation: worker crash doesn't affect main process
    try {
        let result = worker.send_sync(Command::HeavyTask)
    } catch (e) {
        print("Worker failed, restarting...")
        let new_worker = spawn.process WorkerService { id: 2 }
    }
}
```

## Best Practices and Common Pitfalls

### Recommended Practices

```js
// ✅ Prefer immutable borrow (default is immutable borrow, zero keywords)
fn process_data(data: User) {
    // Most scenarios only need read access
    print(data.name)
}

// ✅ Be explicit with mutable borrow using mut
fn update_user(u: mut User, changes: UserUpdate) {
    u.name = changes.name
    u.email = changes.email
}

// ✅ Use shared with lock for multi-threaded shared state
let app_cache = shared Cache { data: map<string, Data>{} }
spawn async {
    lock app_cache {
        app_cache.data.set("key", value)
    }
}

// ✅ Use spawn.process handle directly for IPC
let worker = spawn.process WorkerService { id: 1 }
worker.send(Message::Task(data))
```

### Common Pitfalls

```js
// ❌ Pitfall 1: Accidental ownership transfer
fn example() {
    let data = load_data()
    spawn async {
        process(move data)  // data is transferred
    }
    // print(data)  // Error: data is invalid
}

// ✅ Solution: Use shared or copy
fn example_fixed() {
    let data = shared load_data()
    spawn async {
        lock data {
            process(data)
        }
    }
    print(data)  // Still valid
}

// ❌ Pitfall 2: Expensive operations inside lock
fn bad_lock_usage(state: shared AppState) {
    lock state {
        let result = expensive_computation()  // Blocks other threads
        state.result = result
    }
}

// ✅ Solution: Minimize lock scope
fn good_lock_usage(state: shared AppState) {
    let result = expensive_computation()  // Compute outside lock
    lock state {
        state.result = result  // Only hold lock when necessary
    }
}

// ❌ Pitfall 3: Ignoring process crashes
fn example() {
    let worker = spawn.process WorkerService { id: 1 }
    worker.send_unchecked(Command::Risky)  // May crash
}

// ✅ Solution: Use try/catch
fn example_fixed() {
    let worker = spawn.process WorkerService { id: 1 }
    try {
        worker.send(Command::Risky)
    } catch (e) {
        // Gracefully handle crash
        let new_worker = spawn.process WorkerService { id: 2 }
    }
}
```

## Comparison with Traditional Languages

| Feature | XULO | Rust | Go | C++ |
| --- | --- | --- | --- | --- |
| Memory Management | Ownership + Borrowing | Ownership + Borrowing | GC | Manual/GC |
| Syntax Style | Keywords (`mut`, `move`) | Symbols (`&`, `&mut`) | No explicit management | Manual management |
| Default Behavior | Immutable borrow | Mutable borrow | Value copy | Value copy |
| Thread Safety | Compile-time checks | Compile-time checks | Runtime detection | No guarantees |
| Process Isolation | Built-in Actor model | No built-in | Goroutines | No built-in |
| Learning Curve | Medium | Higher | Lower | High |

XULO's design goal is: **To maintain Rust-level safety while providing simpler syntax and lower cognitive load**.
