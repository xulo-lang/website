## Import / Export

XULO uses `export` for module-level exports and `pub` for type member visibility.

```js
// Export (export declaration)
export fn add(a: number, b: number): number {
  a + b
}

export let PI = 3.14

export type User = {
  name: string
}

export enum Status {
  Active
  Inactive
}

// Re-export current module declarations
export { add, PI }

// Re-export from another module
export { add, PI } from './math'
export { default as Logger } from './logger'

// Import
import { add, PI } from "math"
import type { User } from "types"
import * as math from "math"
import "core"
```

**Import Forms:**

| Form | Meaning |
|------|---------|
| `import { a, b as c } from "..."` | Named import |
| `import type { T } from "..."` | Type-only import (erased at runtime) |
| `import * as ns from "..."` | Namespace import |
| `import "..."` | Side-effect import |

**Export Forms:** Two forms, both starting with `export` — `export fn/let/type/enum` (declaration-level), `export { a, b }` (re-export, optionally with `from`).

## `export` Keyword (Module-Level Export)

`export` is a declaration-level modifier that marks a declaration as public (visible to other modules):

```js
export fn add(a: number, b: number): number { a + b }
export let PI = 3.14
export enum Status { Active Inactive }
export type User = { name: string }
```

- `export fn/let/type/enum` only affects cross-module visibility; within the module, use as normal
- `export { a, b }` re-exports names already declared in this module
- `export { a, b } from './module'` re-exports content imported from another module
- `export fn main` and `fn main` are both recognized as program entry points

> Note: `import type` is written after `import` (`import type { ... }`), not inside the braces.
> The `default` keyword has been removed and is reserved (XULO has no default exports); cross-module exports use `export`, imports use named imports.

## Visibility & Encapsulation Specification

### Module Level

Use `export` to control whether types, functions, and constants are exposed externally. Items without `export` are only visible within the current `.xulo` file.

```js
// Exported: other modules can import
export struct User { ... }
export fn create_user(): User { ... }

// Private: only available in current file
struct InternalCache { ... }
fn helper(): string { ... }
```

### Type Member Level

Struct (`struct`) fields and methods are **private by default**. Use `pub` to explicitly mark a field or method as public:

```js
export struct User {
    pub name: string     // Public field, externally readable/writable
    age: number          // Private field, only accessible within this module
}

impl User {
    // Constructor (externally callable)
    pub fn new(name: string, age: number): User {
        User(name: name, age: age)
    }

    // Public method (externally callable)
    pub fn get_age(self): number {
        self.age
    }

    // Private method (only available in this file)
    fn validate_age(age: number): boolean {
        age >= 0
    }
}
```

### Two-Level Division

| Level | Keyword | Controls | Example |
| --- | --- | --- | --- |
| **Module Level** | `export` | Whether type/function/constant is exposed | `export struct User` |
| **Type Member Level** | `pub` | Whether field/method is externally accessible | `pub name: string` |

**Core Rule**: If a `struct` does not have `export`, even if its fields have `pub`, external modules cannot import this `struct` at all.

## Language Comparison

| Concept | Module Export | Member Visibility |
| --- | --- | --- |
| **XULO** | **`export`** | **`pub`** (private by default) |
| **TypeScript** | `export` | `public` / `private` (public by default) |
| **Swift** | `public` | `public` / `private` |
| **Rust** | `pub` (file/mod level) | `pub` (struct field level) |

## Import Resolution Rules

- Relative paths or locally existing module names (e.g., `./math`, `math`) → resolve to local `.xulo` files, included in bundle
- Other specifiers (e.g., `@xulo/ui`) → treated as external packages, generated as ESM `import`
- `import type` is for type checking only; at runtime, value bindings are preserved only if the imported name is also a runtime value, otherwise completely erased
- **No runtime module loader**: each file compiles to an IIFE that returns an export object, dependencies inlined in topological order into a single JS file
- Circular imports (A → B → A) are rejected

## Cross-Module Calls

- Imported functions preserve parameter names, supporting named argument calls
- Importing non-existent export names reports a semantic error
- `trait` is an exportable type member (`export trait`), imported via `import type { Trait } from "./mod"`; `impl` blocks are not portable across modules and must be declared locally in the module that uses the trait
