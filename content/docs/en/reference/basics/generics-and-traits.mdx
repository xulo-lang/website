## Type Parameters

A generic declaration writes `<…>` immediately after its name. Functions, `struct`s, `enum`s, `type` aliases, and `impl` blocks may all be parameterized; a `trait` never is (see [Traits](#traits)).

```js
fn first<T>(xs: List<T>): T { xs[0] }
struct Pair<K, V> { key: K, value: V }
enum Either<L, R> { Left(L), Right(R) }
type Wrapper<T> = List<T>

struct Holder<T> { value: T }
impl<T> Holder<T> {
  fn get(self): T { self.value }
}
```

**Rules:**

- One parameter list per declaration, comma-separated with distinct names — `<T, T>` is ill-formed.
- A parameter list has **no default type arguments**: every argument of an application is written or inferred; there is no `T = Int` form.
- A parameter is in scope for the whole signature and body (and every field, payload, or aliased type). It is a type name, never a value: no runtime representation and no expression position — and never a constructor: applying a type parameter, `T<Int>`, is ill-formed (`E0230`).
- Naming convention: a single letter (`T`, `U`, `K`, `V`) or an UpperCamelCase descriptive name.
- Generic method and variant access use ordinary spelling: `x.method()` with `.`, variants with `::` (`Either::Left(1)`).

### Nested Angle Brackets

`>>` is one token (right shift), so two closing angle brackets must never touch — write a space:

```js
let nested: List<Map<String, List<Int> > > = []
```

| Form | Well-formed |
|------|-------------|
| `List<List<T> >` | yes |
| `List<List<T>>` | no — `>>` reads as the shift operator |

### Type Applications

A type application `Name<Args>` may be written wherever a type is expected — an annotation, a field, a payload, an alias, a parameter or return type, a pattern's type. Four rules make it well-formed; all violations are `E0230`:

- The argument count must equal the declaration's parameter count: `Map<String>` and `Pair<Int, String, Int>` are ill-formed.
- A generic name never appears without its arguments: `let xs: List = []` is ill-formed, not shorthand for anything.
- A non-generic name takes no arguments: `Int<String>` is ill-formed.
- A type parameter is never applied: `T<Int>` stands for a proper type, not a family of them.

```js
let ok: Map<String, Int> = {}         // well-formed
// let bad: Map<String> = {}          // error: `Map` expects 2 type arguments, found 1 (E0230)
// let bare: List = []                // error: `List` expects 1 type argument, found 0 (E0230)
```

Type arguments are never written at a call site (see [Inference](#inference)); written arguments differ from inferred ones only in syntax — they are unified and bound-checked exactly the same way.

## Bounds

```js
fn area_of<T: Area>(shape: T): Float { Area.area(shape) }
fn perimeter_of<T>(shape: T): Float where T: Area { shape.perimeter() }
fn render<T: Area + Scalable>(shape: T): Float { … }
```

- `<T: Trait>` and `where T: Trait` are equivalent; a parameter must not be bounded in both places. A `where` clause follows the return type and precedes the body — and may follow only a **function** signature: `struct`, `enum`, `trait`, `type`, and `impl` declarations use the inline `<T: …>` form.
- Multiple bounds are joined with `+`, never with `&` — `&` builds an intersection *type* a value has, while `: A + B` restricts what may be substituted for a parameter.
- A bound must name a trait visible at the declaration site (`E0806`), and it names a trait, never an application of one: `<T: Convert<String>>` is `E0811` — a trait is not a type constructor.
- A bound is a constraint, not subtyping: a `T: Area` value is not an `Area`; inside the body it exposes the members the bound declares.
- **Bound checking.** Every type argument — inferred at a call or written in a type application, for a function, `struct`, `enum`, alias, or `impl` — must satisfy every bound of its parameter (`E0801`), even when the argument was inferred rather than written:

```js
trait Area { fn area(self): Float }
struct Palette<T: Area> { shape: T }

let ok = Palette(shape: rect)       // T = Rect, and Rect: Area
// let bad: Palette<Int> = …        // error: `Int` does not implement `Area` (E0801)
```

- A type satisfies a bound exactly when a visible `impl` for the bound's trait **applies** to it — including that impl's own bounds holding in turn (see [Traits](#traits)). There is no structural fallback and no second source of evidence.

## Inference

Type arguments are **never written at a call site**: `first<Int>(…)` and `Map<String, Int>(…)` are not part of the language. Arguments are inferred by unification against the declared parameter types, and an expected type may supply what the arguments leave open.

```js
let n = first([1, 2, 3])        // T = Int
let s = first(["a", "b"])       // T = String
// let bad: String = first([1, 2])   // error: T is already Int

fn empty<T>(): List<T> { [] }
let ys: List<Int> = empty()     // OK: T from the expected type
let xs = empty()                // error: T not determined (E0216)
```

- Every type argument must satisfy the parameter's bounds (`E0801`), whether it was inferred at a call or written in an annotation.
- A parameter occurring twice in a signature receives one solution; when two constraints demand different types, the later argument is reported as a mismatch against the type the earlier one fixed (`E0202`):

```js
fn both<T>(a: List<T>, b: List<T>): T { a[0] }
let t = both([1], ["x"])   // error: T is Int from `a`; `List<String>` does not match `List<Int>` (E0202)
```

- Each distinct assignment of type arguments is a separate instantiation: the program behaves **as if** a non-generic copy were written for each, and no operation observes a type argument at runtime.

## Traits

```js
trait Area {
  fn area(self): Float;
  fn perimeter(self): Float
}

struct Rectangle { w: Float, h: Float }

impl Area for Rectangle {
  fn area(self): Float { self.w * self.h }
  fn perimeter(self): Float { 2.0 * (self.w + self.h) }
}
```

**Declaration:**

- A trait declares **no type parameters**: `trait Convert<T> { … }` is a compile-time error (`E0810`), and a trait's method signatures therefore never mention type parameters. A type that should convert to several targets implements one trait per target, not one parameterized trait.
- Method signatures are separated by `;` (a trailing `;` is optional).
- A trait method is signature-only — **no default implementations**, and every method must declare a return type.
- The receiver is `self` or `mut self`; an implementation must use the same form, and remaining parameters must be annotated.
- `pub trait` exports the trait; importers use `import type { Area } from "…"` and implement it locally.

**Implementation:**

- Every declared method must be present (`E0802`) with mutually assignable signatures (`E0803`), and no extra methods may be declared (`E0804`) — extra behavior belongs in an inherent `impl`.
- Two implementations of the same trait for the same type in the same module are `E0805`.
- An `impl` applies within the module that contains it: **importing a type or trait never imports an `impl`**.
- **A generic `impl` applies to a type** only when its parameters can be instantiated so the implemented type equals that type **and** its bounds are satisfied by that same instantiation — recursively, an impl whose bounds name other traits applies only when those bounds hold in turn. An impl that does not apply contributes **nothing**: no members through member lookup (a lookup left with only it is `E0102`) and no trait implementation for explicit dispatch or bound checking (`E0801`).

```js
struct Palette<T> { shape: T }
struct Rect { w: Float, h: Float }
struct Dot { r: Float }

impl Area for Rect {
  fn area(self): Float { self.w * self.h }
}

impl<T: Area> Palette<T> {
  fn render(self): Float { Area.area(self.shape) }
}

let ok = Palette(shape: Rect(w: 3.0, h: 4.0))
print(str(ok.render()))          // works: Rect: Area, so the impl applies

// Palette(shape: Dot(r: 1.0)).render()
// error: no member `render` on `Palette<Dot>` (E0102) — `T: Area` is not satisfied
```

## Dispatch

```js
fn main() {
  let r = Rectangle(w: 3.0, h: 4.0)
  print(str(Area.area(r)))      // explicit dispatch
  print(str(r.area()))          // member call
}
```

- **Explicit dispatch** `Trait.method(receiver)` resolves directly to the implementation of `Trait` for the receiver's static type; if none is visible, that is `E0801`.
- **Member calls** `value.method(…)` resolve in a fixed order: inherent `impl` methods of the receiver's type first, then trait methods in scope. No candidate is `E0102`; more than one is `E0809` and must be disambiguated with `Trait.method(receiver)`.
- All dispatch is static. There is no dynamic dispatch on a value's runtime type and no reflection over type arguments.

### Inside a Bound

```js
fn describe<T: Area>(shape: T): Float {
  shape.area() + Area.area(shape)   // both forms, one target
}
```

- A member call on a type parameter resolves **through a bound** — the bound is its only source of members. An unbounded parameter has no members: `t.area()` inside `fn f<T>(t: T)` is `E0102`.
- Both `x.method()` and `Trait.method(x)` are legal wherever `T: Trait` is written, and both denote the same static call.
- The implementation a bound uses is the one visible at the point that **selects the type argument** — a call that infers it or a type application that writes it; it travels with the bound into the generic body. Two instantiations at call sites in different modules may therefore use two different implementations — that is specified behavior, not an ambiguity.

## Structural vs Nominal

- A type satisfies a trait **only through an `impl`**. Matching field shapes never implies satisfaction.
- A `type` alias is transparent: it never causes a type to implement a trait, and no `impl` may be declared *for an alias* — implementations attach to the type it expands to.
- `ToString` is built in: interpolating a value in a template requires a base type (`Int`, `Float`, `Boolean`, `String`) or `impl ToString` (`E0212`).

```js
struct User { name: String, age: Int }

impl ToString for User {
  fn to_string(self): String {
    `${self.name} (${self.age})`
  }
}
```

## Example

```js
trait Area {
  fn area(self): Float;
  fn perimeter(self): Float
}

struct Rectangle { w: Float, h: Float }
struct Circle { r: Float }

impl Area for Rectangle {
  fn area(self): Float { self.w * self.h }
  fn perimeter(self): Float { 2.0 * (self.w + self.h) }
}

impl Area for Circle {
  fn area(self): Float { 3.14159 * self.r * self.r }
  fn perimeter(self): Float { 2.0 * 3.14159 * self.r }
}

fn area_of<T: Area>(shape: T): Float { Area.area(shape) }

fn main() {
  let r = Rectangle(w: 3.0, h: 4.0)
  let c = Circle(r: 2.0)
  print(str(area_of(r)))       // 12
  print(str(area_of(c)))       // ~12.57
}
```

`area_of` is checked once per instantiation against `Area`; `Rectangle` and `Circle` satisfy the bound through their `impl`s.

Bounds, inference, and monomorphization are specified in the [generics spec](/en/docs/spec/types/generics/), and dispatch in the [traits spec](/en/docs/spec/types/traits/).
